# 0.1.27 — the scanner could not see the client the scaffold ships

Origin: `gate6`, plugin 0.1.26, 2026-09-04. Found by `mavci-architect` while
planning task 0001, which escalated it rather than working around it silently;
verified independently against the scanner and the shipped scaffold before it was
filed. Queued as finding 4 in `pending-system-change-0.1.26.md`.

---

## 1. The defect

`lib/sitescan.mjs` recognised a service-role client by one of two shapes:

    ADMIN_FACTORY   getSupabaseAdminClient | createSupabaseAdminClient | getServiceRoleClient
    INLINE_ADMIN    createClient(...) with SUPABASE_SERVICE_ROLE_KEY within 400 chars

The scaffold this plugin ships exports `createAdminClient`
(`templates/scaffold/lib/supabase/server.ts`), and builds it with
`createServerClient` from `@supabase/ssr`. **Neither name was in either pattern.**
Two independent misses, stacked: the factory name and the constructor name.

Measured on gate6, a project created by `/mavci-core:new-project` and otherwise
unmodified. The scaffold's own Stripe webhook constructs a service-role client at
line 28 and queries with it at line 29. The scan excluded that line with reason
`no_admin_client` — whose text is *"file constructs no service-role client"*,
which is false about that file — and reported `sites_total: 0`.

So `supabase.service_role_query_scoped` was blind to every query made through the
scaffold's own factory, and reported green by seeing nothing. Every project the
generator creates inherited it.

**It was harmless on that one query only by luck.** `stripe_events` has no tenant
column. A `createAdminClient` query against `orgs`, `members` or any tenant table
would have been equally invisible, and guardian would never have been dispatched
to ask about it.

## 2. Why the residue control did not catch it

The residue is the one control in that file designed to catch shapes nobody
anticipated: *a site this scanner can neither enumerate nor name is a FAILURE, not
a skip*. It did not fire, and the reason is worth keeping.

An unrecognised factory did not fall through to residue. It was **confidently
classified** as `no_admin_client` — an exclusion that asserts a fact about the
file. The residue only catches hits that reach no branch; this one reached a
branch and the branch was wrong. A control that catches unanticipated shapes does
not help when the shape is anticipated and the answer is mistaken.

## 3. Why eleven releases of assertions passed

`check-service-role-sites.mjs` had two negative controls, both good, both run
against fixtures under `templates/fixtures/supabase.service_role_query_scoped/`.
Those fixtures spell the factory using a name the scanner already knew. **They
test the rule against inputs written to satisfy it** — the adjacent assertion, not
the one that mattered. This is the sixth time this repository has recorded that
shape.

## 4. The fix

**Derive the factory names from the code, not from a list.**
`discoverAdminFactories(ctx)` walks the project before any file is scanned: a
module that builds a client with a service-role key, and exports a function,
exports a service-role factory — whatever the project calls it. The project-wide
pass is necessary because the module that *builds* the client is almost never the
module that *queries* with it; `server.ts` contains no `.from(` at all, so it was
never even opened.

The name list is kept as a fallback, with `createAdminClient` added, because
removing a name a project might already use would be a regression.

Deliberately coarse in the safe direction: every exported name in such a module is
attributed, not only the enclosing function. That over-enumerates rather than
under-enumerates, and a false site is a question guardian answers and a reviewer
dismisses, while a false exclusion is a query nobody ever looks at.

## 5. The second defect, which the first was hiding

Fixing the enumeration immediately made the scaffold's `stripe_events` insert a
site — and `supabase.service_role_query_scoped` would then have flagged it as a
blocker, **in every project built from the scaffold, on the scaffold's own code**.

That is a false positive, and it exposed a gap between the rule and its own
description. The description has always said *"Every service-role query against a
TENANT table"*. The rule never checked tenant-table-ness at all; it asked only
whether a predicate was present. Nobody noticed, because the only query that would
have revealed it was invisible.

The rule now derives non-tenant tables from the migrations and skips them, and it
**fails closed**: a table is treated as non-tenant only when a migration creates it
and that `CREATE` carries no tenant column. A table nothing creates — a schema
built in a dashboard, a migration the parser cannot read — stays a finding.
"No evidence it is tenant-scoped" and "evidence it is not" are different facts, and
only the second is a reason to be silent.

A checker whose first act on a new project is to flag the template it just wrote
teaches the operator that the checker is wrong. That is the cost this avoids, and
it is worth more than the one finding it suppresses.

## 6. The assertion, and the broken build it catches

`check-service-role-sites.mjs` gains **N3: the shipped scaffold is the fixture.**
It scans `templates/scaffold/` and asserts the webhook's service-role query is
enumerated as a site and is *not* excluded as `no_admin_client`.

Demonstrated failing against the 0.1.26 behaviour (factory discovery disabled and
the name removed from the fallback list): exit 1, two failures naming exactly this
defect.

One honesty note recorded in the file itself: the third N3 assertion — that the
factory is discovered — **passes even on the broken build**, because it calls the
derivation directly and never asks whether `scanProject` uses it. It is a unit
check on the derivation and is explicitly not the control. The two that go through
the wiring are.

If the scaffold ever builds a service-role client this scan cannot see, N3 fails —
whatever the factory ends up being called, and without anyone having to remember
to add a name in two places.
