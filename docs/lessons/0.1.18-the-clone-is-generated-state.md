# 0.1.18 — the clone is generated state, and nothing said so

Raised on 2026-09-02, in this repository, after 43 files and 2510 insertions of
0.1.18 were found sitting **uncommitted in the marketplace clone** at
`~/.claude/plugins/marketplaces/mavci` — a directory whose entire contract is
that it gets overwritten.

The work was recovered intact. That is the only reason this is a lesson and not
an incident, and the margin was **twenty-seven minutes**: the next `git fetch`
had not run yet. Nothing detected it, nothing warned, and nothing would have
reported it afterwards.

---

## Why it is the most dangerous near-miss so far

Every failure this system has found until now announced itself. The Stop gate
exited 0 where it meant to exit 2, and eight verdict files recorded it. The
account check fired in the wrong place, and `Repository not found` was printed
four times. `check-pretag` ran 13 of 17, and the four it skipped were passing
anyway. **Each of them left a trace someone could eventually read.**

This one leaves none. The propagation procedure in `CLAUDE.md` runs

    git fetch origin
    git checkout -B main origin/main

in the clone, once per machine per release. `checkout -B` against a dirty tree
discards uncommitted content **silently** — no prompt, no error, no reflog entry
for content that was never committed. There is nothing to recover from and
nothing to notice.

And the first symptom is the worst possible one: **CI passing on a version that
does not contain the fix.** The tag is cut, the suite is derived from
`release.yml`, every check runs, every check passes — because the checks are
real and the code they were meant to guard is simply not there. A green release
run is the system's strongest signal, and it would have been telling the truth
about a tree that had silently lost twenty-seven minutes of work.

---

## Half one — why it happened

**The operator's, not the agent's.** The instruction to `cd
~/.claude/plugins/marketplaces/mavci` was given for a `git rm`, which is a
legitimate thing to do in a clone. Work then simply continued in the directory
the session was already sitting in. No rule was broken, because there was no
rule.

That is the whole mechanism, and it is worth stating plainly rather than
dressing up: **a working directory is sticky, and a one-off `cd` into generated
state is indistinguishable from a `cd` into a source tree.** Nothing about the
clone looks different. It is a git repository with the same files, the same
branch name and the same remote as the repository it was cloned from. Every
reflex that makes an agent productive in a source tree — edit, run the checks,
iterate — is exactly wrong there, and produces no feedback at all.

The clone is a **consumer**, not a source. Nothing written there survives.

---

## Half two — what should prevent it

Three layers were considered. The cheapest is now built; the stronger two are
recorded here, not built, and the reason is given.

**Built in 0.1.18 — `doctor` FAILs when the clone has uncommitted changes.**
`checkDistribution` already resolves the clone path and already shells out to
`git`, so this is the layer that cost almost nothing. It reports the clone path,
names the files, names `git checkout -B main origin/main` as the command that
will destroy them, and prints the recovery below. It **FAILs** rather than
warns: a dirty clone is always one of exactly two things, and both need a
person — work about to be lost, or a consumer someone has hand-edited. There is
no third reading in which it is fine.

It is asserted in both directions, because this is a FAIL on a directory that a
developer machine can dirty for ordinary reasons, and *a control that fires
wrongly is a control that gets turned off* (0.1.12 item 5). A clean clone must
produce no failure; a clone `git` cannot read is UNKNOWN, never clean.

**Not built — a hook that refuses edits under `~/.claude/plugins/` when the
source repo exists on this machine.** This is the layer that would actually stop
the write rather than report it afterwards, and it is the right long-term
answer. It is deferred because it is not a small change made carelessly: the
guard would run on every `Write`/`Edit` on the machine, including in unrelated
repositories, and `hooks.json` entries are the surface that shipped **zero
hooks** in v0.1.2 and were silent about it. It also needs a rule for the
legitimate case — `git rm` inside the clone is a real operation — so "refuse
edits here" is not yet a decidable predicate. Filed rather than guessed at,
which is the standing rule for hook payloads in this repository.

**Not built — the deeper fix, which is that propagation should not need a
writable clone at all.** Recorded as a question for a later release, not as a
design.

## The recovery path, because it is not obvious

`git apply` on a PowerShell-produced patch **failed on every hunk**. Two causes,
both structural rather than bad luck: PowerShell's redirection re-encodes the
patch (UTF-16LE, or UTF-8 with a BOM, neither of which `git apply` reads as the
bytes `git diff` produced), and the diff contained **renames**, which a patch
round-trip flattens into delete-plus-add and then fails to apply against a tree
that still holds the original.

What worked, with no transformation whatsoever:

    git -C <clone> add -A && git -C <clone> commit -m "wip: recovered"
    git -C <system-repo> fetch <clone-path> main
    git -C <system-repo> cherry-pick FETCH_HEAD
    git -C <clone> fetch origin && git -C <clone> checkout -B main origin/main

**Git to git, never through a file.** A clone is already a git remote; there is
no reason to serialise a diff to move commits between two repositories on the
same disk. The patch file is a lossy intermediate that exists only because it is
the first thing anyone reaches for.

Verified by comparing tree hashes rather than by reading the diff: source
`a928e82` and cherry-pick `7bceec9` both resolve to tree
`30b0101fa578d810e11595a717c764117fb9b2ae`, on the same parent `6af89de`.
**Identical trees on identical parents is the whole proof** — a diffstat showing
the expected file count would have looked equally reassuring and asserted
nothing about content.

## What this says about the class

The eighteen findings before this one were all about a control that was present
and wrong. This is the first about a **place the system does not look at all.**

`doctor` inspects the clone's *version* and has since 0.1.5 — it reads
`marketplace.json`, reads `plugin.json`, and compares. It walked past the
working tree every single time. The probe was already standing in the right
directory asking a narrower question, which is the same shape as
`check-pretag` calling `git ls-remote` twice and misreading the answer: **the
evidence was in hand and the question was never asked.**

The test that separates them is the one already written down, and it applies
unchanged here: *what would a broken build look like, and would this say so?* A
clone holding twenty-seven minutes of unsaved work looks exactly like a clean
one — to everything except `git status`, which nothing ran.
