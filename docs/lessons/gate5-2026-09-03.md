# Finding 3 - /mavci-core:ship's preflight router call drops the operator's request, and the ship-side call is untested

Filed: 2026-09-03T19:24:00Z, plugin 0.1.23.

Filed by: the main session, driving the first end-to-end run of the chain on gate5.

Target: `skills/ship/SKILL.md` line 12, and the orchestrator's test surface.

`/mavci-core:ship "<request>"` was invoked with a real request. The preflight substitution
on line 12 read `node "${CLAUDE_PLUGIN_ROOT}/scripts/route.mjs" 2>&1` - no `--request`, no
`$ARGUMENTS`. route.mjs parses the request out of argv (`argv.indexOf('--request')`), so it
received `request = null` and took the no-request branch at lib/route.mjs:236, printing
`next: release_gate -> the operator`. Per ship's own action table `release_gate` means STOP,
so the chain terminated before its first router consultation, on a request that routes to
`plan` the moment the argument is passed. Line 45 - the loop body's call, inside a fenced
block - does carry `--json --request "$ARGUMENTS"` and is correct. The defect is that the
line which actually executes at skill-load time is not the line that was written to be right,
and it is the one the operator meets first.

The failure is silent and reads as a legitimate verdict. `release_gate` is a real action with
a plausible explanation attached, so a dropped argument is indistinguishable from a project
genuinely sitting in the release phase. It only fails this way when `state.phase === 'release'`;
from `idle` the same drop yields `idle`, which is also a stop and also looks correct. There is
no input for which the bare call is right and no output that announces it was wrong.

Fix applied in the cache copy for this project, unreleased: line 12 becomes
`!`node "${CLAUDE_PLUGIN_ROOT}/scripts/route.mjs" --request "$ARGUMENTS" 2>&1``. Passing it
unconditionally is safe - all three request-sensitive branches sit inside the no-task-open
arm, so the router ignores `--request` whenever a task is open, exactly as SKILL.md line 47
already states. Bare `/mavci-core:ship` expands to `--request ""`, and `""` is falsy, so the
continue-the-open-task form degrades to precisely today's behaviour rather than to a new one.

### The assertion, and the broken build it must catch

The existing test calls the router as a pure function with a request already in hand. It
asserts the callee and assumes the caller. **The missing assertion is caller-side and belongs
to the skill, not to route.mjs:** extract the `!`...`` command from `skills/ship/SKILL.md`
and assert that every invocation of `route.mjs` in that file passes `--request "$ARGUMENTS"` -
the preflight on line 12 as much as the loop body on line 45. Broken build this must catch:
the one shipped today, where 0.1.23's route.mjs is correct on every enumerated case, its
tests all pass, and `/mavci-core:ship "<anything>"` on a project in the release phase cannot
start a task.

Generalise it, because ship is not the only caller and the next one will be written the same
way: for every SKILL.md that declares `$ARGUMENTS` in its body, assert that each script it
invokes through `!`...`` either receives the arguments or is on an explicit allowlist of
calls that legitimately take none. Audited today at 0.1.23 - ship is the only skill with the
defect. `doctor` forwards `$ARGUMENTS` (unquoted, which is correct there: doctor.mjs reads
only flags). `plan`, `build`, `verify`, `scribe`, `retro`, `waive` and `new-project` bind
`$ARGUMENTS` into prose for the model and preflight scripts that take no argument -
`state.mjs --show`, `gate.mjs`, `retro.mjs --list` - which is correct. `verify` line 15 calls
`route.mjs` bare and is ALSO correct: its `$ARGUMENTS` is a task id, not a request, and the
router has no task-id parameter. The allowlist is what keeps that last case from being
"fixed" into a bug.

This is the same shape as the counter split: each side right in isolation, the seam between
them asserted by nothing. Every router case is tested as a pure function; nothing tests that
the caller hands it what those cases are about.
