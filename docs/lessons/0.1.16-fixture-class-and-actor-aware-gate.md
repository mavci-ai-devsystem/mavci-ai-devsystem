# 0.1.16 — the fixture class, the actor-aware gate, and a reader for the ticket

Built from three findings raised in project **gate4c** against 0.1.15, filed via
`/mavci-core:retro` and queued in that project's
`.mavci/lessons/pending-system-change.md` (findings 3, 6 and 7).

All three came out of one event: a `mavci-guardian` dispatch against worklist
`wl-20260901194633` that looped ten times and produced nothing.

---

## Finding 7 — the corpus deadlock (the fix the other two hang off)

gate4c holds the guardian acceptance corpus in `corpus-run/`. Every corpus file
references `SUPABASE_SERVICE_ROLE_KEY` deliberately — that is what makes it a
fixture — so `next.no_service_role_client` and `next.env_centralised` marked all
of them as new blockers, and `gate.mjs` refused **every subagent stop in the
repository**. Meanwhile `doctor --preflight` FAILed at SessionStart for having no
corpus result for 0.1.15. Neither state could produce one.

The exemption existed as a *concept*: `rules/index.mjs` skipped
`plugins/mavci-core/templates/fixtures` in the secrets check, commented
"fixtures carry fake keys on purpose". Two things made it unreachable — it lived
inside `secrets.no_committed_secrets` rather than the rules that were firing, and
the path it exempts is inside **this** repository, so no project tree could ever
match it. There was no per-project fixture concept in any rule.

### The change

`checks.fixtures` in the manifest: repo-relative directories whose files are
exempt from `FIXTURE_EXEMPT_RULES` — and that set is exactly
`next.no_service_role_client` and `next.env_centralised`.

Four constraints, each load-bearing:

1. **Declared, never inferred.** A directory does not earn an exemption by being
   called `fixtures/`. Silencing the checker by choosing a filename is not a
   control.
2. **An allow-list of rules**, enforced inside `isDeclaredFixture` rather than at
   each call site, so a rule cannot opt itself in by calling the helper.
3. **`secrets.no_committed_secrets` can never be exempted.** It is the one check
   that is neither baselineable nor waivable. A fixture holds a placeholder; if
   it holds a live key the finding is correct.
4. **The declaration is itself checked**, by the new `config.fixture_scope`.
   `fixtureRoots()` drops unsafe entries *before* they take effect, so
   `fixtures: ["."]` cannot exempt the rule that objects to it.

### What the fix uncovered

`checks.exclude_paths` already existed, drops files from the scan **entirely and
before every rule** — the secrets check included — and shipped with no
description, no constraint and nothing checking its contents. A narrow fixture
class beside an unconstrained blanket escape is theatre, so `config.fixture_scope`
polices both fields: the two are one decision, "what does the checker not look
at", and splitting them would let a reader fix the narrow one while the wide one
stayed open.

**Do not baseline a corpus.** It records deliberate fixture content as project
debt and makes the baseline permanently untrue.

## Finding 6 — a blocking reason the actor cannot act on is a trap

Guardian has `allow: []` and `native_constraint: true` in `agent-scopes.json`:
`Edit` is absent from its context entirely. The gate blocked it ten times with
"Fix these, then stop again" over paths it had no grant to touch — sixteen
verdict files in 137 seconds, ending at the retry ceiling with exactly the
information attempt one had. On those files the remedy was also *actively wrong*:
"move the reference into a server-only module", applied to a fixture, means
delete the defect the fixture exists to carry.

This is 0.1.12's "a blocking gate closes the operator channel" arriving at the
**agent** instead of the operator, and it reproduced at main-session scope one
turn after it was filed: `corpus-run/**` is outside the main session's `Edit`
allow-list too.

### The change

`stoppingActor()` in `gate.mjs` resolves the write grant of whoever is stopping —
`agent-scopes.json` for a subagent, the committed `permissions.allow`/`ask` rules
for the main session. When **every** blocking finding names a path outside that
grant, the gate records the verdict and **releases**, with an `AUTHORITY:` note
naming the operator. This is the `rules/index.mjs` remedy-authority mechanism
applied to the gate: the rule knows what kind of actor a remedy needs, but only
the gate knows which actor is actually standing there.

Deliberately narrow. It does **not** release on `authority` alone — a project
whose only blockers are `legal.pages_present` (authority `external`) must keep
blocking, because the agent genuinely can act by stopping and reporting, and
releasing there would let legal debt through on a technicality. An **unknown**
grant never buys a release either, or every unparsed payload becomes a way past
the gate.

## Finding 3 — the witness that had no reader

The guardian ticket is written before dispatch and deleted on exactly one path: a
record was written. So an open ticket means *a dispatch happened and produced no
record*. Three components documented it as the signal —
`guardian-record.mjs`, `worklist.mjs` and the guardian skill all said "the gate
sees it" — and a grep for the path found exactly one consumer: the component that
writes it. `gate.mjs` contains no reference to guardian or tickets. Neither does
`doctor.mjs`. `release-gate.mjs` reads records only.

The entire signal that a run had been lost was one stderr line from a hook, in a
session that then ended.

### The change

`checkGuardianTicket` in `doctor.mjs`. FAIL, naming the worklist id, when a
ticket is open and no record for it exists; WARN when the record exists but the
ticket survived (a failed unlink, not a lost run). Not gated on session age: the
writer deletes the ticket the moment it records, so a ticket doctor can see is
already one no record closed, and an age test would hide a run lost earlier in a
session still running.

## The assertions, and the broken builds they were run against

Every one was demonstrated failing first. This is the house rule and it is the
rule this release was most at risk of skipping, since all three fixes are
"obviously correct" by inspection.

| assertion | broken build | observed failure |
|---|---|---|
| `next.no_service_role_client` and `next.env_centralised` pass a `good/corpus-run/` file | `isDeclaredFixture` stubbed to `false` | both reported "fired on its good/ fixture"; the other 13 rules stayed green |
| guardian is released on the FIRST stop | actor-release branch disabled | `exit=2 kind=block`, remedy naming a file guardian cannot write |
| the release names the path and carries `AUTHORITY:` | same | absent |
| builder is still BLOCKED on `lib/**` | — | control: stayed green throughout, proving the release discriminates |
| unknown `agent_type` is blocked | — | control: stayed green |
| doctor FAILs naming `wl-CI-LOST-RUN` | `checkGuardianTicket` call commented out | both ticket assertions failed; the "record exists" control stayed green |

The gate assertion is on **whether the turn is allowed to end**, not on the reason
text. Asserting the reason names the file passes against 0.1.15 — the reason was
present, correct, and repeated ten times, which *is* the failure. That is the
`check-gate.mjs` trap from Gate 4 (payload asserted, exit status never), and it
was the live risk here.

The doctor assertion is on **the worklist id reaching the output**, not on doctor
exiting non-zero: doctor already exits non-zero on a fresh fixture for other
reasons, so an exit-status-only assertion passes against a doctor that never
opens the file.

## Caught during the work, worth keeping

The first `globToRe` in `gate.mjs` used a NUL byte as the placeholder holding
`**` while `*` was substituted. `check-plugin.mjs` caught it — invariant 3, no
NUL bytes, because such a file shows as "Binary files differ" and is skipped
silently by `grep -r`. The gate's own actor logic would have become invisible to
every audit that greps the tree. It is now scanned character by character, with
no placeholder to get wrong.

Also observed, and already queued in gate4c as an addition to 0.1.12's finding 5
rather than a new entry: `risk-guard.mjs` refused a `retro.mjs --record` call
because the **finding text** quoted a control-plane path as a string operand —
the exact case the guard's own refusal message calls "fine and not what this is
about". The finding was re-filed with the path written less precisely, so the
false positive has stopped costing only turns and started degrading filed
evidence. The `Edit` arm resolves the target correctly; only the Bash arm matches
command text, so that fix has a working model to copy rather than one to design.
