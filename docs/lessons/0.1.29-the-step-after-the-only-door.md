# 0.1.29 — the step after the only door

**2026-09-04.** Finding 22, and the second half it required.

---

## What happened

`check-pretag.mjs --cut` has been the only door to a release tag since v0.1.9,
and its header says why in a sentence that has held up better than the code
under it:

> a check nobody is required to run is the same failure one layer up.

That sentence is the reason `--cut` *creates* the tag rather than advising one.
It stopped being applied exactly one step later. `--cut` created the tag, printed

    git push origin <tag>
    gh run watch "$(gh run list --workflow release.yml ...)"

and exited. Everything after the tag existed was advice, and on 2026-09-04 both
halves of it failed, silently, in the same session.

**`--cut` can create a tag in a directory that gets reset.**
`~/.claude/plugins/marketplaces/mavci` is a real checkout of this repository —
same remote, same branch, same workflows, same `plugin.json`. Every arm of the
gate passes there. Propagation into it is `git fetch origin` then
`git checkout -B main origin/main`, which discards whatever is there with no
prompt and no reflog entry for content never committed. That is 0.1.18's finding
about the clone, arriving at the one step that is irreversible.

**And a push can report nothing to send.** `git push --follow-tags`, run from the
repository the operator IS editing, answers `Everything up-to-date` — correctly,
because the tag is not in that repository.

**Neither is visible from the other's output.** The tag-creation output says a tag
was created, the push output says there is nothing to send, and both are true. The
first symptom is the signal 0.1.18 already named as the worst this system has to
give — **CI green on a version that does not contain the change**, because the
checks are real and the code is simply absent.

---

## The two questions, settled from the architecture

### Where does the assertion live?

`--cut` cannot make it after `--cut` exits. So either `check-pretag` grows a
second mode the operator runs after pushing, or the premise changes.

A second mode is **advice with a different shape**. It is the same object the
header already ruled on: something correct, computable, and not required. This
repository has watched that shape fail at every scale it has — a Stop gate that
emitted the right JSON and exited 0, a `check-pretag` array that named 13 of 17
checks, a `retro --apply` that wrote into a directory nobody would open. The fix
each time was to put the thing behind a door that already exists.

**So the push moved inside the gate, and the watch with it.** `--cut` creates the
tag, lets `check-tags.mjs` judge it, pushes it, reads it back off origin, and
polls the release run to a bound.

**v0.1.17's paragraph arguing the opposite is rewritten, not left standing.** It
said:

> `--cut` creates the tag LOCALLY and pushes nothing, so a credential that cannot
> write fails at the operator's own `git push`, immediately and in words, with the
> tag still local and deletable. The failure is loud and free to undo.

Every clause of that is true and none of it argues against pushing here. It
describes a property — *a write failure must leave the repository as it was* — and
assigns it to the operator's memory. The `push-failed` arm preserves the property
exactly and performs the rollback. A recorded decision reversed without its
paragraph being rewritten is how a governing document comes to show the broken
form as canonical (ARCHITECTURE 6.4's `hooks.json` example, which showed the array
form that made v0.1.2 install with zero hooks).

**The push is by explicit refspec.** `git push origin refs/tags/<tag>` — never a
bare `git push`, never `--tags`. Both of those can answer "Everything up-to-date"
and send nothing, which is the observation this whole release exists because of.

### What does it assert?

Three facts had to be checked by hand after every release:

1. the tag reached origin
2. the release run started
3. the release run passed

**It takes all three.** The first by reading the tag back off the remote; the
second and third by polling the run to a bound.

---

## Atomicity, which is the property that makes a failure survivable

**Every arm up to and including the push leaves either the tag on origin or no tag
at all — never a local tag that origin does not have.** A failed `--cut` is
therefore retryable by re-running the same command, and nobody has to work out
which of three places the tag is in before they can act.

This reversed a decision taken inside this release. The first build kept the local
tag on `absent` and on `unknown`, reasoning that it was the evidence. It is not
worth much as evidence — the commit is still HEAD and re-cutting produces an
identical tag — and it costs the thing that actually matters at that moment, which
is a state with one possibility in it rather than three.

`unknown` deletes for the same reason and says precisely what that establishes and
what it does not:

> The local tag was deleted, so this is now either on origin or nowhere — never a
> third state. This gate has NOT established which, and does not guess.

That is the shape 0.1.12's finding 5 is about, in the last place it could still do
damage: the message must not name a cause the gate has not established.

**From the watch onward the direction reverses and nothing is rolled back.** The
tag is on origin, immutable, and possibly already fetched. A machine that has
fetched a tag keeps the object it holds, so a moved tag means one name and two
commits. `watchRelease` is not even given a git runner — a function that cannot
reach git cannot be talked into un-pushing a released tag by some later edit — and
every arm of it that is not a pass says the tag stands.

---

## The bound, and what it says at the bound

Ten minutes total, two of them for the run to appear at all, polled every fifteen
seconds. `release.yml` installs Claude Code and runs the full suite, so a healthy
run is minutes; ten is roughly double, which is the shape a bound should have —
long enough that hitting it means something, short enough that a release does not
hang on a queue nobody is watching.

**Still running when the budget is spent is UNKNOWN.** Not a pass, because
invariant 5 says a failed probe is never reported as one. Not a failure, because
the tag IS released and calling it a failure invites the one repair that must
never happen.

So three exit statuses, because they are three different answers:

| exit | meaning |
|---|---|
| 0 | the tag is on origin and its release run passed |
| 2 | a refusal — up to and including the push, nothing was released |
| 3 | the tag is on origin and the verdict could not be read |

Collapsing 3 into 2 would report a released version as a failed cut. The message
at the bound names the elapsed bound, says the tag was NOT deleted and must not
be, gives `gh run watch <id>`, and says what each outcome means: if it passes the
release is good and nothing further is owed; if it fails the tag stands and the
fix is a NEW version.

Five watch verdicts rather than two, because collapsing them is how a message
explains one cause confidently and wrongly: `passed`, `failed`, `unfinished`,
`no-run` — which says outright that it is **not** evidence the workflow failed to
trigger, since GitHub creates runs asynchronously and a queue can exceed the bound
— and `unavailable`.

## The refusal names what it refuses and why, in its first sentence

> REFUSING: a release cut in generated state is not a release — this is the
> marketplace clone, and the tag you are about to create would be destroyed by the
> next propagation into it, unread by anybody.

The path comes after that, and the propagation command after the path. Somebody
who hits this needs to understand what would have happened to their tag, not that
a path check failed. `retro --apply` got this refusal in v0.1.25, for the same
reason and by the same argument, after it wrote a finding into the clone and
reported success.

**The predicate is the class, not the instance.** Everything under
`<config>/plugins` is written by `/plugin` and replaced by it — the clone and the
plugin cache both live there — so containment is what refuses. The clone is
*additionally* matched by canonical path, because a development machine can hold
it as a junction or a symlink and a lexical test would miss that entirely.

## Verification

Nine assertions were red against the 0.1.28 tree before anything was implemented,
with assertion 16 — *a source checkout is NOT reported as generated state* — green
throughout. That is the half that matters when a control is being **added**: a
refusal that fired on a source checkout would refuse every release on every
machine, and a guard that fires wrongly is a guard that gets turned off.

Twenty-one mutations, each producing labelled red. The interesting rows are the
ones that found something rather than confirming something.

| P1 | no refusal at all (0.1.28) | 17, 17b, 18, 19 |
| P2 | the clone matched lexically only | 19 — the junction case |
| P3 | only the clone refused, not the class | 18 |
| P4 | the verdict computed, `main()` ignores it | 19 |
| P5 | `push --tags` instead of an explicit refspec | 20, 26 |
| P6 | no rollback on a failed push | 21 |
| P7 | an unpushed tag left behind on absence | 22 |
| P8 | a failed probe treated as an answer | 23 |
| P9 | the commit on origin not compared | 24 |
| P10 | the green cut stops naming the manual links | 25 |
| P11 | check-tags rejects and it is pushed anyway | 27 |
| P12 | the predicate fires on a source checkout too | 16 |
| P13 | the watch runs when the tag never arrived | 26b |
| P14 | the watch verdict discarded; a push is always a pass | 25b, 26c |

### Three of them were findings, not confirmations

**P21 — nothing asserted the sentence.** Replacing the entire first line with
`REFUSING: generated state.` left every assertion green. They all read the body,
where the path was still printed and the propagation command still quoted three
lines down. The requirement had no assertion behind it until the mutation said so.
Assertion 17b anchors on the first line and requires the consequence to appear
*before* the path.

**P11 crashed the suite instead of failing it.** Assertion 27 was written before
`cutTag` took a `watch`, so killing the check-tags arm walked into an undefined
call. A crash reports nothing about which arm broke — it is a red run with no
finding in it. Fixed, and the assertion now also requires that a rejected tag is
never watched.

**P19b could not be caught at all.** A poll loop with no bound does not fail an
assertion, it **hangs the suite** — which is the one shape of "no bound" the bound
assertion most needs to catch, and the suite would simply stop producing output.
The fake `gh` now refuses to answer past a ceiling and every watch assertion routes
through one helper, so an unbounded loop is four labelled reds naming `UNBOUNDED`
instead of a stalled run.

### And P12, which is the one that generalises

The generated-state refusal was placed **first** in `main()`, ahead of the
`--selftest` dispatch. It looked obviously right: refuse before anything, including
the informational no-argument path that reads a `plugin.json` which is not the one
being edited.

With the predicate mutated to fire on every tree, the gate refused to run **its own
self-test**. The mutation reported *no failures at all* — assertion 16, which
exists precisely to catch an over-firing predicate, was the first thing the
over-firing predicate took offline.

That is 0.1.26 section 4's pattern at a fifth scale: *the artefact written to
prevent a defect contains the defect.* Comment, fixture, lesson file, assertion —
and now a placement decision, where the control disabled its own detector.
**Nothing static could have found it**: reading the placement shows a control
placed early, which is what a control placed early looks like.

`--selftest` is the one mode that can neither report on a release nor create one,
so it is the one mode the refusal must not reach. It is dispatched first now, with
the reason written at the line.

**And the note is no longer only here.** A lesson file that sat in the directory
being written into did not bind, once, and that is the third scale in the list
above. So the rule now sits above `selftest()` in `check-pretag.mjs`, where the
next person adding an assertion to that file reads it before they add one: *a green
mutation is a finding about the assertion, always — never evidence that the fix was
unnecessary*, with all five scales named and the closing line that
`check-ci-gates.mjs` proves an assertion CAN fail and says outright that it cannot
prove any of them discriminates.

### The tail had to be extracted before it could be tested

Through v0.1.28 the tag-create / check-tags / push sequence lived inline in
`main()`, where no test could reach it — which is exactly where v0.1.26 found
finding 25 sitting for three releases. `cutTag` is that sequence with all three
runners injected, and two ordering properties are asserted directly:

- **the rollback fires before anything is pushed.** A sequence that pushed first
  would roll back identically, exit identically, and look the same in every other
  respect — while origin kept the tag it had already been sent.
- **the watch fires only after the tag is confirmed on origin, and not at all when
  it is not.** Watching for a run of a tag that is not there polls to its bound and
  reports UNKNOWN, burying the one thing that IS known.

### The residual, named rather than covered

`cutTag`'s sequence is asserted with every runner faked. What is **not** asserted
is `main()` calling it: a release gate cannot cut and push a real tag to prove that
it does. That is one line, it is commented at the call site, and no check pretends
otherwise. Naming it is the alternative to a check that appears to cover it.

---

## What is not proposed

Nothing here reads a report. 0.1.24's finding stands unchanged: **the evidence for
"this landed" is the filesystem**, and no assertion is proposed for it,
deliberately, because nothing in this repository can read a transcript and a check
that appeared to would be the house failure mode exactly. What changed is that all
three of the facts that used to be checked by hand after a release are now made by
the gate that owns the step — and where it cannot make one, it says UNKNOWN and
leaves the tag alone.
