# 0.1.22 — the transition with no middle

Applied from gate4c findings 27 and 28, filed 2026-09-02 against plugin 0.1.21.

## What shipped

**One sanctioned plan transition.** `state.mjs --begin-plan "<title>"` allocates the
task id, writes both task halves, records the task on the state and enters the plan
phase — in a single write to `state.json`. `skills/plan/SKILL.md` steps 2 and 3
collapse into it. `--set-phase` and `--new-task` both remain: `--set-phase` for the
other three transitions, `--new-task` agent-safe and phase-free for `connect`'s
per-baselined-check allocation.

**`active_task` acquired a writer.** It had none. `--init` stamped it `null` and
nothing set it again, anywhere in the plugin.

**Three version facts, three fields.** `ci_pinned_plugin_version` (the tag CI
clones, moved only by `--init` and `doctor --sync`), `written_by_plugin_version`
(stamped by `setState` on every write), and `plugin_version` retained as a
read-only legacy key that the first write migrates.

**`doctor --sync` writes through the sanctioned writer.** It was a bare
`fs.writeFileSync` followed by `--reseal`, so the one write that set the pin
skipped schema validation and redaction and the seal then certified a document
nothing had validated — while `CLAUDE.md` states the control plane is written only
by `state.mjs`.

## Why, and the two fixes that were rejected

gate4c, 2026-09-02, two consecutive Bash calls in one session, same script, same
quoting, differing only in the flag:

    14:06:17Z  state.mjs --set-phase plan   ->  "phase = plan", EXIT=0
    14:06:29Z  state.mjs --new-task "..."   ->  denied by the harness classifier

`risk-guard.mjs` classifies `--new-task` AGENT_OK and `--set-phase` PRIVILEGED,
describing the latter in its own words as *the gate deciding whether app code is
writable at all*. Two external gates ordered that risk backwards: the privileged
write went through unconfirmed, the agent-safe one was refused.

**The guard did not fail.** Its main-session branch deliberately exempts
`--set-phase` from even a confirm, which is correct — a slash command with a human
present is who that door is for. There was no defect in mavci's guard, and the
first reading of the incident (that there was) was wrong.

**What made it worth a release is the reading of the block.** Something stopped the
session, so the guard looked alive; the gate that fired was not ours, and the write
we actually care about had already landed ten seconds earlier. Reporting *"I was
blocked, the control plane held"* would have been another green probe on the half
that worked. A block is not evidence that the right thing blocked — this repository's
own failure mode, arriving from outside the system, where nothing we write can order it.

We cannot make two external classifiers agree with our risk ordering and we do not
need them to. We need the sequence to have no interruptible middle for their
decision to land in.

Two smaller fixes were considered and refused:

- **`--new-task` moving the phase.** It is AGENT_OK and `connect` calls it once per
  baselined check, so this hands the app-code gate to an unattended subagent — a
  privilege escalation dressed as an atomicity fix, refused by the architecture's
  own rule that authorisation is by caller.
- **`--set-phase` refusing to enter plan with no task.** There is no such state to
  test. `next_task_id` always increments, and `{phase: plan, active_task: null}` is
  exactly what `--init` writes, so the refusal would reject every fresh project's
  first legal transition — and it guards the write that succeeded, not the one that
  vanished.

## Why the two changes shipped together

`--begin-plan` needs `active_task` to have a writer or the halt stays undetectable,
and both the `active_task` writer and the version-field split change `state.json`.
Finding 24's propagation window is walked into once rather than twice.

## THIS IS THE SECOND CONTROL-SCHEMA CHANGE IN TWO RELEASES

0.1.20 added `library_fingerprint` to `guardian-corpus.schema.json` and that is
finding 24: under `additionalProperties: false`, a field added by the new writer is
not merely unknown to the previous release's still-registered hooks, it is a
violation, and the gate blocked with a remedy (`--reseal`) that could not clear it.

**Why this was not combined with 0.1.21's change.** It could not have been. 0.1.21
was cut on 2026-09-02 before either finding existed: finding 27 was filed at 14:4xZ,
after the halt that produced it at 14:06Z, and finding 28 came out of checking 27.
Combining them would have meant holding 0.1.21 for a defect nobody had observed yet.
That is the honest reason, and it is not a good one to repeat: two schema changes in
two releases means two propagation windows in two days, and the next control-schema
change should wait for a third rather than make it three.

**The window, stated as the release requires.** A session that registered 0.1.21's
hooks and then has 0.1.22 propagated onto disk will run 0.1.21's `state.schema.json`
against documents written by 0.1.22's `state.mjs`, and `ci_pinned_plugin_version`
and `written_by_plugin_version` will be rejected as unexpected properties. It lasts
until the next session start.

**RESTART THE SESSION AFTER PROPAGATING 0.1.22, BEFORE ANY COMMAND WRITES
`state.json`.** `--begin-plan`, `--new-task`, `--set-phase` and `doctor --sync` all
write it. If the gate blocks with an unexpected-property rejection naming either new
field, the remedy is the restart and not `--reseal`: the rejection is the schema, not
the seal, and resealing spends an operator action to arrive back at the same block.

The reverse direction is handled and does not need a restart: 0.1.22 accepts the
legacy `plugin_version`, `mavci-verify.yml` falls back to it, and the first write
migrates it into `ci_pinned_plugin_version`. Already-connected projects stay valid
without operator action.

## The check

`scripts/ci/check-state-transition.mjs`, registered in `selftest.yml` and
`release.yml`. Every assertion in it was watched failing against 0.1.21 before any
fix was written.

Its first run recorded the house failure mode inside itself, which is why the
control probe exists. The atomicity assertion — *a failed task write leaves
state.json byte-identical* — printed `ok` against 0.1.21, because `--begin-plan` did
not exist, the run failed before writing anything, and the file was therefore
unchanged. A probe that passes because its subject is absent. It now runs the legacy
`--set-phase`/`--new-task` sequence under the same blocked task write first and
requires that to half-commit; if the fixture cannot move state.json, every atomicity
assertion below it is reported as inert rather than green. The atomicity assertion
also refuses to report a pass when `--begin-plan` is missing, in those words.

The adjacent assertions that pass and prove nothing, named in the file so nobody
adds them back as coverage: *`--set-phase` sets the phase*, *`--new-task` creates a
task*, *`--init` stamps the running version*. All three are true, all three are
green, and none of them can see any of this — each tests one half of a pair whose
failure lives in the gap between them, or one version agreeing with itself. The
third is the same blind spot as `doctor`'s unreachable skew branch, which compared
the loaded plugin against its own copy and reported agreement.

The naive fix is guarded too: restamping everything in `setState` satisfies the
`written_by_plugin_version` assertion and silently repins CI from any machine with a
newer plugin installed, so an ordinary `--new-task` must leave
`ci_pinned_plugin_version` byte-identical.

## Not fixed here

tagged, so `main` is two commits ahead of `v0.1.20`. Tagging is the operator's.
