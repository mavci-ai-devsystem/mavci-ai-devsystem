# Pending system change — doctor cannot see the version it is running

Recorded: 2026-08-29
Target: `scripts/doctor.mjs` (`checkHookRegistration`), `scripts/state.mjs` (`pluginVersion`)
Occurrence: third of the wrong-gate shape (after 0.1.2's zero registered hooks, 6.24's
untested agent-scope self-test). Same shape: the probe and the thing it claims to prove
were never connected.

## What happened

A session ran with 0.1.9's hooks after 0.1.10 was installed. Every visible signal was green:

- `claude plugin install` reported success
- `installed_plugins.json` recorded `0.1.10` for both the user and project scope,
  installPath `.../mavci-core/0.1.10`, at 2026-08-29T20:03:11Z
- every install check in doctor passed
- the hooks Claude Code actually invoked in that session were 0.1.9's

Nothing reported the divergence. A gate ran, produced a verdict, and the operator had no
way to know which rule set produced it.

## The correction — the check already exists and cannot fire

The obvious fix is already implemented, and has been since at least 0.1.9:
`doctor.mjs:962` FAILs when `hook-run.json`'s `plugin_version` differs from the installed
version, and it already names "Restart the session" as the fix. Adding it is not the change.

It cannot fire, because both sides of the comparison come from the same stale copy:

- `state.mjs:51` — `pluginVersion()` reads `PLUGIN_ROOT/.claude-plugin/plugin.json`, and
  `PLUGIN_ROOT` is `path.resolve(dirname(import.meta.url), '..')` (`state.mjs:34-35`) —
  the directory of the *running* script.
- `/mavci-core:doctor` is dispatched by the session's loaded plugin, so under stale hooks
  `doctor.mjs` is 0.1.9's copy and `pluginVersion()` returns `0.1.9`.
- `hook-run.json` was stamped by the same 0.1.9 hooks, so `newest.plugin_version` is
  `0.1.9` too.

`'0.1.9' !== '0.1.9'` is false. The branch is unreachable in exactly the situation it was
written for. It compares the loaded plugin against itself and reports agreement.

## The change

`checkHookRegistration` must compare the **loaded** version against an **external**
authority, not against itself. `checkInstallScope` (`doctor.mjs:412`) already reads that
authority — `~/.claude/plugins/installed_plugins.json`, whose records carry `version` and
`installPath`.

1. Add a helper that returns the newest `version` recorded for `PLUGIN_ID` in the
   registry, and null when the registry is missing or malformed (registry reads are
   already treated as could-not-check, never a crash — keep that).
2. In `checkHookRegistration`, FAIL when the registry version differs from
   `pluginVersion()`, with the named fix: **restart the session** — the plugin was
   updated on disk but this session still holds the old copy. Keep the existing
   `hook-run.json` comparison; it catches the case where the command and the hooks
   diverge from each other.
3. WARN, do not FAIL, when the registry is unreadable: unknown is not passing, and
   section 11 requires this toolchain to run where Claude Code is not installed.

Optionally assert the same on the path: `PLUGIN_ROOT` against the registry record's
`installPath`. It is the same fact and a stronger statement of it.

## Why this one matters

The operator can find the other two shapes by looking. This one is invisible from inside
the session: the report is generated by the stale code it would have to indict. Until the
comparison reaches outside the running plugin, "doctor is green" carries no information
about which rule set is enforcing anything.

## Verification

Not repairable from inside a stale session — the fix ships in the system repo. It is
verified by installing a new version mid-session and confirming doctor FAILs *before* the
restart, not after. Apply with `/mavci-core:retro --apply`, or delete this file.

# Pending system change 2 — the gate blocks with an empty reason

Recorded: 2026-08-29
Target: `scripts/gate.mjs` (`emitContinue`, `failClosed`, the fail path at ~line 372)
Occurrence: fourth of the wrong-gate shape, observed live in the same session that
recorded the first. This one was caught *by* running the gate, not by reading it.

## What happened

The gate was given a known blocker — `next.supabase_client_in_function` at
`app/audit/page.tsx:14` — and a turn was ended deliberately to see whether it would stop.

It did, and the detection is exactly right. Verdict
`.mavci/control/verdicts/adhoc-1788034434762.json`, plugin_version 0.1.10:

    check_id: next.supabase_client_in_function
    path:     app/audit/page.tsx   line: 14
    evidence: createClient called at module scope
    severity: blocker
    summary:  { blockers: 1, fail: 5, pass: 11 }  verdict: fail

`gate-run.json` recorded `outcome: "fail"`, and the stop WAS refused — the turn resumed.
Detection works. Blocking works.

**The agent was told nothing.** The entire Stop hook feedback was:

    [node .../0.1.10/scripts/gate.mjs]: No stderr output

The gate had already assembled the perfect message — check id, path, line, evidence and
the full remedy string — in `detail` at the fail path. None of it arrived.

## Why

`emitContinue` (`gate.mjs:154`) writes to **stdout**:

    {"hookSpecificOutput":{"hookEventName":"Stop","continue":true,"stopReason":"..."}}

then `process.exit(2)`. Both halves of the "belt and braces" are fastened to nothing:

> **Corrected 2026-08-29, after the decision-control table was loaded verbatim.** Point 1
> below was wrong as originally written, and wrong in the direction that would have misled
> the next reader: it named `continue` as the defect and treated the nesting as incidental,
> when the nesting was the whole defect and `continue` did nothing at all. The original
> text is kept struck through rather than deleted, because "the diagnosis was plausible and
> wrong" is the fact worth carrying forward. See NATIVE-CAPABILITIES 4.5, resolved 0.1.11.

1. ~~**`continue: true` says do not stop.** It is the literal opposite of the intent. Only
   the exit code is blocking; the payload, if it were read, would wave the turn through.~~

   **What is actually true: `continue: true` was inert, not inverted.** It is a universal
   field — "`continue` | `true` | If `false`, Claude stops processing entirely after the
   hook runs" — so it defaults to true and acts only when set to false. Setting it to true
   said nothing and changed nothing. It goes anyway, because inert noise in a blocking
   payload is one more thing a future reader has to work out is meaningless, but removing
   it fixes no bug. Nothing in 0.1.10's behaviour is explained by it.

2. **`hookSpecificOutput` is not the carrier for a Stop decision — and this alone is the
   defect.** For a Stop hook the model-facing fields are top-level `decision: "block"` with
   `reason`. The only `hookSpecificOutput` field `Stop` honours is `additionalContext`
   (plus the required `hookEventName`), so a `stopReason` nested there is a field of no
   documented shape and renders **no decision at all**. Because no JSON decision was made,
   resolution fell through to the other carrier — "the reason from your JSON's blocking
   decision when it makes one, and your stderr text otherwise" — and `gate.mjs` wrote
   nothing to stderr. Hence, exactly, "No stderr output". Top-level `stopReason` would not
   have helped either: it is "Message shown to the user when `continue` is `false`. Not
   shown to Claude."
3. **Exit 2 blocks using `stderr` as the reason, and gate.mjs writes nothing to stderr.**
   Hence, precisely, "No stderr output": a refusal with an empty explanation.

The 0.1.10 note at `gate.mjs:150` ("NATIVE-CAPABILITIES 4.5, corrected in 0.1.10") records
fixing the *previous* version of this bug — emitting without exiting 2, which recorded
failing verdicts throughout Gate 4 and never blocked once. The exit was added. The payload
was moved into a shape that carries no decision, and the stderr path was never wired.
0.1.9 blocked nothing; 0.1.10 blocks silently.

## Why this is worse than it looks

`readContinues` increments per `prompt_id` and the gate stops blocking at
`GATE_MAX_CONTINUES`. An agent that is refused without being told why cannot fix the
violation — so it stops again, identically, until the ceiling is spent and the gate
gives up and lets the violation through. The mechanism designed to prevent an
unsatisfiable gate from spinning is instead the exit path for every real one.

## The change

1. Write `detail` to **stderr** before `process.exit(2)`, in both the fail path and
   `failClosed`. This is the mechanism that actually delivers, and it is the one belt
   that currently carries nothing.
2. Fix the JSON payload to a real Stop decision: top-level `{"decision":"block",
   "reason": detail}`. Drop `continue: true` from every blocking path — it contradicts
   the exit code it ships with.
3. Keep `emitMessage`/`hookSpecificOutput` for the non-blocking paths (the pass-with-debt
   note and the ceiling-reached note), where a `systemMessage` is the right carrier.
4. **Add a self-test that asserts the reason text reaches the recipient**, not merely that
   the exit code is 2. Every previous occurrence of this shape passed a probe that checked
   the wrong half. A test asserting `exit === 2` would have passed here too.

## Verification

Re-run this exact experiment: restore a known blocker, end a turn, and assert the Stop
feedback names `next.supabase_client_in_function` and `app/audit/page.tsx:14`. The gate
under 0.1.10 fails that assertion today.

## Note on the defect used as the probe

`app/audit/page.tsx:14` has been fixed — `createClient()` now runs inside `AuditPage()`.
The module-scope client was a genuine multi-tenant bug, not only a test fixture: one
client shared across requests can serve one tenant's session to another tenant.
